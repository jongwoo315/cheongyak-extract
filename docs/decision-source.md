# 결정 기록: 어떤 방식을 왜 골랐나

세 결정의 사실과 출처만 적었다. 「고른 방식과 이유 (jw)」 칸은 jw가 `labels/source-judge.json`의 `jw` 칸을 채운 뒤 직접 쓴다.
숫자의 바탕은 절마다 다르다. 1절과 2절은 재는 공고 20건 × 필드 8개 = 160칸, 3절은 PDF에만 있는 필드 3개를 기존 50건(150칸)과 새 30건(거주지만 30칸)에서 잰 값이다. #183에서 주소 정규화(쉼표·괄호)를 바꿔 `truth-check`·`source-judge`·`regex-new`·`regex-vs-llm` 리포트를 다시 만들었다. 아래 숫자는 다시 만든 리포트 기준이다.

## 1. 정규식 대 LLM (#150)

- 정규식은 필드 8개마다 라벨 뒤의 값을 줍는 단순한 패턴이다. 다듬는 공고 29건으로 규칙을 만들고 고정한 뒤 재는 공고 20건을 한 번 쟀다
- 재는 20건 160칸에서 정규식은 맞음 112(70.0%)·비움 34(21.2%)·다른 값으로 채움 14(8.8%)다
- 같은 칸에서 LLM(T0, C안)은 맞음 154(96.2%)·비움 0·다른 값으로 채움 6(3.8%)이다
- 칸마다 보면 정규식 맞음·LLM 틀림 2칸, 정규식 틀림·LLM 맞음 44칸, 둘 다 틀림 4칸, 둘 다 맞음 110칸이다
- 갈리는 필드: 당첨자 발표일(정규식 4칸 대 LLM 20칸)·계약일(9 대 20)·시공사(10 대 19)
- LLM 20건의 입력 토큰 합계는 1,908,990이다. 정규식은 LLM을 부르지 않는다
- 정답은 청약홈 상세 HTML이다. 이 정답이 맞는지는 아래 2번에서 다룬다
- 출처: `reports/regex-vs-llm.md`, `reports/regex-new.md`, `reports/extract-new.md`

## 2. HTML 대 PDF (#153, 이번)

- HTML 쪽은 청약홈 상세 HTML 표에서 읽은 값이다(`truth.parse_truth`, 필드 8개). PDF 쪽은 공고문 PDF에서 읽은 값이다. 시스템이 쓰는 LLM 추출 값과, 구현 루프가 PDF를 읽고 적은 `labels/pdf-values-20.json`(칸마다 근거 줄·쪽)이 있다
- HTML 값과 PDF 값이 정규화 뒤 다른 칸은 2칸이다(다른 값 2). #153 때는 5칸(표기 차이 3, 다른 값 2)이었고, 표기 차이 3칸은 주소의 쉼표·괄호 차이라 #183에서 같은 칸이 됐다. 출처: `reports/truth-check.md`
- LLM이 HTML과 다르게 채운 6칸 중 4칸은 PDF 값과 같다. 출처: `reports/truth-check.md` 마지막 절
- HTML 값·PDF 값·LLM 값이 정규화 뒤 모두 같은 칸은 156칸이다(#153 때 153칸 + 쉼표·괄호만 달랐던 공급위치 3칸). 이 칸은 두 방식 모두 맞다고 본다는 가정을 깔았다
- 셋 중 하나라도 다른 칸은 4칸이다: 시행사 2(2026000438·2026000437), 시공사 1(2026000314), 입주예정월 1(2026000454). #153 때는 공급위치 3(2026000443·2026000438·2026000437)이 더해진 7칸이었고, jw는 그 3칸을 `둘 다`로 판정했다. 이 판정은 `labels/source-judge.json`에 그대로 있고 `reports/source-judge.md`의 「정규화로 같아져 판정할 칸에서 빠진 칸」 절에 적었다
- 4칸 중 시행사 2칸(2026000438·2026000437)은 HTML 값과 PDF 값이 같고 LLM 값만 다르다(`한국토지주택공사`만 적었다). 이 칸의 `jw`는 HTML과 PDF 중 고르는 것이 아니라 두 값이 맞는지 보는 것이다
- 어느 쪽이 맞는지는 어느 쪽도 정답이라 확실할 수 없어서 코드로 가리지 않았다. jw가 7칸(지금 판정할 칸 4 + 빠진 칸 3)을 보고 `HTML`·`PDF`·`둘 다`·`둘 다 아님` 중 하나를 `labels/source-judge.json`에 적는다
- 판정할 칸이 4칸뿐이라 표본이 작다. 20건 밖 공고에는 LLM 8필드 추출을 돌리지 않았다(비용)
- 출처: `reports/source-judge.md`, `labels/source-judge.json`

## 3. PDF에만 있는 필드 (#152)

- 전매제한 기간·거주지 우선 비율·신혼부부 소득 기준은 HTML에 없고 공고문 PDF에만 있다. 이 세 필드는 HTML 쪽 값이 0칸이라 HTML 대 PDF를 비교할 수 없다
- 거주지는 PDF 안 일반공급 ①지역 묶음이 있으면 그 묶음만 LLM에 준다(149건 중 125건에서 코드가 찾는다)
- 기존 50건(다듬는 공고)에서 정답 있는 칸 중 맞은 칸: 전매제한 47/47, 거주지 48/49, 신혼부부 소득 기준 42/46. 출처: `reports/pdf-fields-tune-2.md`
- 새 30건의 거주지 30칸 중 맞음 29, 다른 값으로 채움 1. 읽은 곳별로 `묶음` 25칸은 25칸 맞음, `전체` 5칸은 4칸 맞음이다. 출처: `reports/pdf-resident-test.md`
- 이 정답은 jw가 아니라 구현 루프가 PDF를 읽고 적었다. 정답 파일 둘(180칸)에서 정답 검사에 걸린 칸은 0이다. 출처: `reports/pdf-labels.md`
- 첫 시도(PR #9)는 재는 30건에서 거주지 20/30이라 반려됐다. 기록: `reports/pdf-fields-test.md`
