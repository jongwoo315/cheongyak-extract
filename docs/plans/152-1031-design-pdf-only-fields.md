# #152 설계 — PDF에만 있는 필드 3개를 수동 정답 50건으로 잰다

## jw 기준

pdf에 있는 필드 3개애 대한 수동 정답이 나오고 점수도 계산한다

## 착수 때 확인한 사실 (2026-10-31, main `8fbe472`)

1. `data/raw/`에 수집된 공고는 150건이다. 2026000235는 텍스트가 없는 스캔 PDF다(#150 `reports/regex-more.md`)
2. 150건 PDF(`pdf_text.pages`, sort=True)에서 키워드가 있는 공고 수: `전매` 148, `해당지역|우선 공급|거주자` 149, `월평균 소득|소득 기준` 138
3. 청약홈 상세 HTML(`detail.html`)에는 `전매`·`월평균소득`이 없다(2026000494·2026000437에서 태그를 지운 텍스트로 확인). `해당지역`은 청약 접수 일정 표의 열 이름으로만 나온다. 세 필드의 정답을 HTML에서 얻을 수 없다
4. 세 필드가 PDF에 적힌 모양
   - 전매제한: 1쪽 요약 표에 `재당첨제한 | 전매제한 | 거주의무기간 | 분양가상한제 | 택지유형` 열이 있고 값이 한 칸이다(2026000494 `6개월`, 2026000437 `3년`). 본문에 「당첨자 발표일로부터 6개월」 같은 문장이 다시 나온다
   - 거주지 우선: 공공택지는 비율로 적는다(2026000437 「평택시 1년 이상 … 30%를 우선 공급 … 경기도 6개월 이상 … 20% … 전국 거주자 … 50%」). 민간 공고는 비율 없이 「해당 주택건설지역 거주자 우선」만 적기도 한다(2026000494)
   - 소득 기준: 특별공급 유형(신혼부부·생애최초·다자녀·노부모·기관추천)마다, 같은 유형 안에서도 우선공급·일반공급·추첨공급마다, 맞벌이 여부마다 % 값이 따로 있다(2026000494 신혼부부 1단계 100%·맞벌이 120%, 2단계 140%·맞벌이 160%). 기관추천은 「해당 없음」이다
5. LLM 추출은 8필드가 `extract.FIELDS`·`OUTPUT_SCHEMA`·`_FIELD_HELP`에 묶여 있고, `llm.LlmAsk`가 `OUTPUT_SCHEMA`를 그대로 쓴다. 8필드 프롬프트를 고치면 `tests/fixtures/llm/prompt.sha256`이 어긋나 녹화를 다시 해야 한다
6. 「수동 정답」을 적을 사람: #149는 구현 루프가 PDF를 읽고 PDF 값을 적었다. jw는 #149 판정 이유에 「llm이 pdf값을 참고하거나 지어낸 경우도 있어서 지켜봐야함」이라고 썼다

## 설계 결정

### 필드 3개의 뜻

소득 기준은 유형·단계·맞벌이마다 값이 갈려(사실 4) 공고 하나에 값 하나로 줄여야 잴 수 있다. 셋 다 공고 하나에 값 하나로 정한다.

| 필드 | 뜻 | 정답 `value` 꼴 | 비교용 정규형 |
| --- | --- | --- | --- |
| 전매제한 기간 | 일반공급 당첨자의 전매제한 기간. 1쪽 요약 표의 전매제한 칸이 있으면 그 값 | `6개월`, `3년`, `없음` | 개월 수 정수 문자열(`6`, `36`, `0`). 주택형·공급 유형마다 다르면 서로 다른 값을 작은 순으로 `,`로 잇는다(`36,60`) |
| 거주지 우선 비율 | 일반공급 물량을 거주 지역별로 나눈 비율, 우선순위가 높은 지역부터 | `평택시 30% / 경기도 20% / 기타 50%`. 비율 없이 해당지역 거주자 우선만 적었으면 `해당지역 100%` | 비율 숫자만 순서대로 `/`로 잇는다(`30/20/50`, `100`). 지역 이름은 비교하지 않는다 |
| 신혼부부 소득 기준 | 신혼부부 특별공급에서 소득 조건이 가장 낮은 첫 단계(우선공급·1단계)의 「도시근로자 월평균소득 대비 %」와 맞벌이 % | `100% (맞벌이 120%)`, 맞벌이 기준이 없으면 `130%` | `100/120`, `130` |

- 신혼부부를 고른 이유: 공공·민간 공고에 모두 있고 소득 % 표가 거의 늘 붙는다. 「특별공급 소득 기준」 전체를 하나로 줄이는 방법이 없다. 생애최초·다자녀 등은 이번에 안 한다
- PDF에 그 값이 없으면(신혼부부 특별공급이 없는 공고, 전매제한을 안 적은 공고) 정답은 null이고 `note`에 찾아본 쪽을 적는다
- 정정 공고가 값을 고쳤으면 고친 뒤 값을 쓰고 `note`에 고치기 전 값을 적는다(#149와 같다)

### 공고 50건

- 대상: `data/raw/`의 수집된 공고 중 PDF 텍스트가 있는 것(2026000235 제외) 149건
- 고르기: pbno를 정렬한 목록에서 `random.Random(152).sample(목록, 50)`. 뽑힌 순서 앞 20건이 다듬는 공고, 뒤 30건이 재는 공고다
- 50건 목록과 나눈 결과를 정답 파일에 같이 적어 다시 뽑지 않아도 같은 목록이 나오게 한다

### 수동 정답 — 누가 어떻게 적나

- **구현 루프가 PDF를 읽고 적는다. jw가 손으로 적는 것이 아니다.** 「수동」은 추출기(LLM 프롬프트)를 돌리지 않고 사람이 읽듯 PDF 텍스트를 읽어 칸마다 적는다는 뜻으로 읽었다. jw가 직접 적기로 바꾸려면 Kickoff에서 바꾼다
- 칸마다 `value`, `quote`(값이 적힌 줄을 PDF 텍스트에서 글자 그대로), `page`, `note`. 형태는 `labels/pdf-values-20.json`과 같다
- 지어낸 값을 막는 검사 둘(사실 6). 코드가 정답 파일을 읽을 때마다 건다
  1. `quote`가 그 쪽 텍스트에 있다(`extract.grounded`)
  2. 정규형의 숫자가 모두 `quote` 안에 있다. 예외는 `3년`→`36`처럼 단위를 바꾼 숫자로, 바꾸기 전 숫자(`3`)가 `quote`에 있으면 된다. `해당지역 100%`는 `quote`에 「100%」가 없어도 된다(비율 없이 적힌 경우의 약속)
- 정답을 다 적고 커밋한 뒤에 세 필드 LLM 추출을 처음 돌린다. 커밋 순서로 확인한다
- jw가 PDF를 열어 확인할 수 있게, PR 본문에 무작위 10칸(`random.Random(1520)`)의 공고·필드·값·쪽·`quote`를 적는다
- 한계: 정답을 적는 쪽도 LLM(구현 루프)이다. 추출 LLM과 같은 쪽으로 틀리면 점수가 실제보다 높게 나온다. 위 두 검사는 PDF에 없는 값을 막을 뿐 해석이 틀린 것은 못 막는다. 그 몫이 PR 본문 10칸이다

### 점수

- 추출기는 LLM 하나다. 정규식 baseline은 이번에 안 한다
- 세 필드를 묶은 프롬프트와 응답 모양을 따로 만든다. 8필드 프롬프트·`OUTPUT_SCHEMA`는 글자 하나 바꾸지 않는다(사실 5). `extract`·`llm`이 필드 묶음을 인자로 받게 하고 기본값을 지금 8필드로 둔다
- 값을 남기는 조건은 지금 기본(C안: 근거 문장이나 값이 그 쪽에 있다)을 그대로 쓴다
- 칸 상태: 정답에 값이 있는 칸은 맞음(정규형이 같다) / 비움 / 다른 값으로 채움. 정답이 null인 칸은 따로 센다 — LLM이 비웠으면 맞음, 값을 채웠으면 「정답에 없는 값을 채움」
- 본 점수: 재는 30건 90칸. 다듬는 20건 60칸 점수는 따로 적는다

### 프롬프트 다듬기

- 다듬는 20건만 보고 프롬프트(세 필드 설명)를 고친다. 최대 3번. 고칠 때마다 무엇을 바꿨고 점수가 어떻게 됐는지 `reports/pdf-fields-tune.md`에 적는다
- 고정한 프롬프트를 커밋한 뒤 재는 30건을 한 번 잰다. 잰 뒤에는 프롬프트를 고치지 않는다(#147·#150과 같다)
