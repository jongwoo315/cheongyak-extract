# #183 주소 정규화에서 쉼표와 괄호를 지우고 같은 값인지 본다 (설계)

**Notion:** #183 · **선행:** #153 (PR #11)

## jw 기준

주소 정규화에서 쉼표와 괄호를 지우고 html과 pdf가 같은 값을 반환한다

## 왜

#153 게이트에서 jw가 공급위치 3칸을 「둘 다」(같은 값)로 판정했다. jw 원문: 「뒤에 붙은 괄호와 쉼표 때문에
다르다고 보이나 실제 텍스트는 동일」. 지금 주소 정규화(`normalize.py` `_address`)는 공백을 한 칸으로 줄이고
괄호 앞뒤 공백만 지운다. 괄호·쉼표 글자는 남아서 세 칸이 다른 값으로 집계된다.

| 공고 | HTML 값 | PDF 값 |
| --- | --- | --- |
| 2026000443 | …5048-5번지 일원 에코델타시티 공동6BL | …5048-5번지 일원 (에코델타시티 공동6BL) |
| 2026000438 | 경기도 평택시 고덕동 고덕면 일원(…A65BL) | 경기도 평택시 고덕동, 고덕면 일원(…A65BL) |
| 2026000437 | 경기도 평택시 고덕동 고덕면 일원(…A12BL) | 경기도 평택시 고덕동, 고덕면 일원(…A12BL) |

## 착수 때 확인한 사실

scratchpad에서 `_address`만 바꿔 끼우고 돌렸다(repo 파일은 안 바꿈). 바꾼 규칙: `(`·`)`·`,`를 공백으로 바꾼 뒤
공백을 한 칸으로 줄인다.

1. `check-truth` 정규화 뒤 같은 칸: 155/160 → 158/160. 공급위치 17/20 → 20/20
2. `judge-source`가 고르는 칸: 7 → 4. 빠지는 칸은 위 공급위치 3칸이다. 남는 칸은 2026000454 입주예정월,
   2026000438·2026000437 시행사, 2026000314 시공사
3. 정규식 20건(`regex-new.md` 공고) 공급위치 맞은 칸: 17 → 18. 정규식 100건(`regex-more.md` 공고) 공급위치는 그대로(99칸 중 다른 값 7)
4. LLM 리포트(`extract-new.md`)는 다시 만들 수 없다. 기본 설정으로 `evaluate`를 돌리면 `data/llm/` 캐시에 없는
   프롬프트라 OpenAI를 부른다(가짜 키로 돌려 401로 멈춘 것을 확인했다). 그 리포트 「틀리게 채운 칸」 표의 공급위치
   2칸(2026000443·2026000437)이 위 표와 같은 쉼표·괄호 차이다
5. 정규화의 주소 종류를 쓰는 필드는 공급위치 하나다(`extract.py:55`)

## 설계 결정

### 1. 규칙 — 쉼표·괄호를 지우는 대신 공백으로 바꾼다

`(`·`)`·`,`를 공백으로 바꾼 뒤 공백을 한 칸으로 줄인다. 지우기만 하면 `일원(평택`과 `일원 (평택`이
`일원평택`·`일원 평택`으로 갈린다. 공백으로 바꾸면 둘 다 `일원 평택`이 된다.

- 대괄호 `[` `]`는 넣지 않는다. jw 기준이 쉼표와 괄호를 말했고, 대괄호가 걸린 칸(2026000508·509, 다듬는 29건)은
  대괄호 위치가 아니라 PDF 텍스트 순서가 바뀐 칸이다
- 이웃 블록이 다른 주소(`AC3블록`·`AC4블록`)는 글자가 달라 다르게 남는다. 기존 테스트가 그대로 지킨다

### 2. 판정 파일에서 빠지는 칸 — jw 판정을 지우지 않고 남긴다

`judge-source`는 지금 판정 파일(`labels/source-judge.json`)의 칸 목록과 이번에 고른 칸 목록이 다르면 에러를 낸다
(`truth_check.merge_judge`). 규칙을 바꾸면 고른 칸이 4칸이 되고 파일은 7칸이라 명령이 멈춘다.

- 파일에는 있는데 이번에 안 고른 칸은 **파일에 그대로 둔다.** 리포트에 「정규화로 같아져 판정할 칸에서 빠진 칸」으로
  jw 판정과 함께 적고, 방식별 합계에서는 세 값이 같은 칸으로 센다
- 이번에 골랐는데 파일에 없는 칸은 지금처럼 에러다. jw가 아직 안 본 칸이다
- 같은 칸의 값이 jw가 본 값과 다르면 지금처럼 에러다
- 안 고른 이유: 파일에서 지우면 jw 판정(「둘 다」와 메모)이 git 기록에만 남는다. 루프가 jw 칸을 지우는 것도 된다
- 방식별 합계는 그대로 159/160이어야 한다. 같은 칸 153+3=156, 남은 판정 HTML 1·PDF 1·둘 다 2

### 3. 다시 만드는 리포트 — OpenAI를 부르지 않는 것만

| 리포트 | 명령 | 바뀌나 |
| --- | --- | --- |
| `reports/truth-check.md` | `check-truth` | 155 → 158 (착수 때 실측) |
| `reports/source-judge.md` | `judge-source` | 판정할 칸 7 → 4 |
| `reports/regex-new.md` | `eval --extractor regex` (20건) | 공급위치 17 → 18 |
| `reports/regex-tune.md` | `eval --extractor regex` (다듬는 29건) | 모름 |
| `reports/regex-more.md` | `eval --extractor regex` (100건) | 그대로일 것 |
| `reports/regex-vs-llm.md` | `python -m cheongyak_extract.compare` | 정규식 쪽만 |
| `reports/normalize.md` | `measure-normalize` | 모름 |

- LLM 리포트(`extract-new.md`·`extract-tune*.md`)는 다시 만들지 않는다. 대신 `extract-new.md` 「틀리게 채운 칸」의
  각 행을 새 정규화로 다시 맞춰 보고, 같아지는 칸 수(예상 2)를 PR 본문에 적는다. 리포트 파일은 고치지 않는다
- 각 리포트를 다시 만드는 명령은 그 리포트를 처음 만든 plan(`docs/plans/14x-*-plan-*.md`)·README에서 찾는다
