# #150 설계 — 정규식 baseline과 LLM 비교

## jw 기준

정규식 baseline과 llm 성능을 서로 비교한다

## 착수 때 확인한 사실 (2026-10-29, main `b16c289`)

1. LLM 결과는 커밋된 리포트에만 있다. LLM 응답 캐시(`data/llm/`)는 #147 세 번째 시도 워크트리 안에 있었고 워크트리를 지울 때 같이 사라졌다. main 체크아웃의 `data/`에는 `raw/`만 있다
2. 그래도 칸마다 LLM이 맞혔는지 알 수 있다. `reports/extract-new.md`(재는 공고 20건, T0, C안)는 정답 있는 칸 160개 중 맞음 154, 비움 0, 다른 값으로 채움 6이고 그 6칸을 공고·필드·추출값까지 표로 적었다. 표에 없는 154칸은 맞은 칸이다
3. 다듬는 공고 29건(232칸)의 LLM 고정 설정 결과는 `reports/extract-tune.md` 마지막 줄이다(C안 맞음 219, 다른 값으로 채움 7)
4. `data/raw/`에는 PDF가 열리는 공고가 150건 있다(#151). 다듬는 29건과 재는 20건을 빼면 101건이 남는다. 이 101건에는 LLM 결과가 없다
5. 추출 결과는 필드마다 `Extraction(value, evidence, page)`이고(`extract.py`), 채점은 `report.metrics`가 정규화(`normalize.py`) 뒤 청약홈 정답과 비교한다
6. `eval` 명령은 시작할 때 `make_ask`로 OpenAI 클라이언트를 만든다(`__main__.py`). 정규식만 돌릴 때도 키가 필요해지면 안 된다

## 설계 결정

### 같은 셋·같은 채점

- 비교의 본 표는 재는 공고 20건 160칸이다. LLM이 쟀던 그 공고, 그 정답, 그 정규화로 정규식을 잰다
- 다듬는 공고 29건 결과도 나란히 적는다. 정규식 규칙은 이 29건만 보고 만든다 — LLM 프롬프트를 다듬은 방식과 같다
- 칸 상태는 #147과 같은 셋이다: 맞음 / 비움 / 다른 값으로 채움. 분모는 정답 있는 칸 수다
- LLM을 다시 부르지 않는다. LLM 쪽 숫자는 커밋된 리포트에서 읽는다(사실 2·3)

### 정규식 추출기의 모양

- `regex_extract(pages) -> dict[필드, Extraction]`. LLM과 같은 꼴을 돌려줘 리포트 코드를 그대로 쓴다
- 근거는 패턴이 걸린 줄, 쪽은 그 줄이 있는 쪽이다
- 「가장 단순한 추출기」로 둔다. 필드마다 라벨(`공급위치`, `입주예정`, `당첨자 발표` 등) 뒤의 값을 줍는 패턴 몇 개다. 표 칸 위치를 세거나 공고별 예외를 넣지 않는다
- 공고 번호·회사명 같은 특정 공고 문자열을 패턴에 넣지 않는다
- `eval --extractor regex`로 고른다. 기본은 지금처럼 `llm`이다. `regex`면 OpenAI 클라이언트를 만들지 않는다

### 규칙을 고정하는 시점

- 다듬는 29건으로 규칙을 고친다. 최대 3번 고치고 고칠 때마다 `reports/regex-tune.md`에 한 줄을 더한다
- 고정 커밋을 먼저 하고 그 뒤에 재는 20건·남은 101건을 잰다. 잰 결과를 보고 규칙을 고치지 않는다

### 남은 101건

- 정규식만 잰다(비용 0). LLM 결과가 없으므로 비교 표에는 넣지 않고 참고로 적는다
- 규칙이 다듬는 29건에만 맞춰졌는지 보는 데 쓴다

## 이번에 안 하는 것

- LLM을 다시 부르는 것. 남은 101건에 LLM을 돌리는 것(약 1,000만 토큰)
- 정답 수동 대조(#149), PDF에만 있는 필드(#152), 결정 기록(#153)
- 정규식과 LLM을 섞는 방식(정규식이 실패한 칸만 LLM에 묻기 등)
- 정규화 규칙 수정
- 정규식이 LLM보다 나아지도록 규칙을 키우는 것. baseline은 단순한 쪽이어야 LLM이 보탠 몫이 보인다
