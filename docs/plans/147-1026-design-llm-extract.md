# #147 설계 — extract() stub을 LLM 추출로 바꾼다

## jw 기준

extract()의 fields에 대한 값들을 llm이 제대로 파싱한다. 파싱하지 못하면 비운다.

## 무엇을 바꾸나

- `extract(pages)`가 지금은 8개 필드를 전부 빈 값으로 돌려준다(#146 stub)
- 이번에 LLM 호출 한 번으로 8개 필드의 값·근거 문장·쪽 번호를 받는다
- 받은 값은 코드가 한 번 더 거른다. 근거 문장이 그 쪽 텍스트에 실제로 없으면 값을 비운다.
  jw 기준의 「파싱하지 못하면 비운다」를 LLM의 말이 아니라 코드가 지키게 하는 자리다

## 착수 때 실측

- 받아 둔 공고문 PDF 3건(2026000518·2026000530·2026000532)은 64·72·73쪽, 텍스트 138,017·177,549·175,352자다.
  빈 쪽은 0개다
- `OPENAI_API_KEY`는 `~/.zshenv`에 있다(orch 세션도 읽는다). `ANTHROPIC_API_KEY`·`GEMINI_API_KEY`는 없다
- 계정에서 쓸 수 있는 모델: `gpt-5.4-mini`·`gpt-5.5`·`gpt-5.6-*` 등(2026-10-26 `/v1/models`)
- 상세 HTML만 있고 PDF가 없는 공고가 7건 더 있다(`data/raw/`). 이번 측정에는 못 쓴다
- 정답의 `공급규모`는 일반분양 세대수 하나다(2026000518 정답 `358세대`, PDF 줄에는 472·114·358·230이 같이 적혀 있다)

## 설계 결정

### LLM 공급자 — OpenAI (Anthropic 아님)

- 이 기기에 키가 있는 것은 OpenAI뿐이다. 같은 기기의 `cheongyak-rag`도 `openai`를 쓴다
- structured outputs(JSON schema `strict`)로 8개 필드 모양을 강제할 수 있어서, 모양이 틀린 응답을 고치는 코드가 필요 없다
- 모델은 환경변수 `OPENAI_EXTRACT_MODEL`, 기본값 `gpt-5.4-mini`. 문서 하나가 대략 입력 10만~18만 토큰이라
  8건이면 100만 토큰 안팎이고, mini 급이면 실행 한 번이 1달러 안쪽이다. 모델 비교는 이번 범위가 아니다

### 문서 전체를 한 번에 넣는다 (쪽 고르기 없음)

- 필드가 흩어져 있다. 일정은 1~2쪽, 공급위치·공급규모는 6~7쪽, 시행사·시공사는 맨 끝(64·72쪽)이다
- 쪽을 고르는 단계를 넣으면 그 단계가 놓친 필드는 LLM이 볼 수도 없다. 오답 원인이 둘로 늘어 측정이 흐려진다
- 쪽마다 `<page n>` 표시를 붙여 넣고, 쪽 번호는 LLM이 그 표시를 보고 적는다
- 컨텍스트 한도를 넘는 공고가 나오면 그 공고를 건너뛰고 이유를 리포트에 적는다(조용히 자르지 않는다)

### 코드가 거르는 규칙 — 값을 비우는 조건

LLM 응답 한 칸마다 아래 중 하나라도 걸리면 그 칸을 `Extraction(None, None, None)`으로 비우고 비운 이유를 남긴다.

1. 값이 비었다
2. 근거 문장이나 쪽 번호가 없다
3. 쪽 번호가 1~쪽수 밖이다
4. 근거 문장이 그 쪽 텍스트에 없다. 비교는 양쪽 공백·줄바꿈을 모두 지우고 한다(#146 리뷰 17 — PDF는 `~\n2026.11.29`처럼 줄이 끊긴다)
5. 응답에 그 필드 키가 없다(#146 리뷰 15 — 키가 빠져도 `KeyError`가 나지 않고 빈 칸이 된다)

값이 근거 문장 안에 들어 있는지는 보지 않는다. `공급규모`는 근거 `… 일반분양 358세대 …`에서 값 `358세대`를 고르는 것이 정상이고,
`계약일`은 근거가 두 줄에 걸친다. 값 자체가 맞는지는 정답과 비교해 잰다.

`Extraction`은 생성 시점에 모순을 막는다(#146 리뷰 16): 값이 없으면 근거·쪽도 없어야 하고, 값이 있으면 근거와 1 이상의 쪽이 있어야 한다.

### 녹화 응답 — CI는 API를 부르지 않는다

- 실제 호출은 프롬프트 sha256으로 `data/llm/` 아래에 캐시한다(git 밖). 같은 프롬프트를 다시 돌리면 API를 안 부른다
- 설계에 쓴 공고 3건의 실제 응답을 `tests/fixtures/llm/<pbno>.json`에 커밋한다. 테스트는 이 응답을 가짜 LLM으로 돌려 거르는 규칙을 통과시킨다
- CI에는 공고문 PDF가 없으므로(`data/raw/`는 git 밖) 녹화 응답 테스트의 쪽 텍스트는 근거 문장으로 만든다. 거르는 규칙과 응답 모양을 재는 테스트지 정확도를 재는 테스트가 아니다

### 측정 — 설계에 쓴 공고와 새 공고를 나눈다

- 프롬프트는 받아 둔 3건만 보고 쓴다. 3건으로 프롬프트를 다듬으면 그 3건 점수는 높게 나오는 것이 당연하다(#148 리뷰 때 같은 지적)
- 프롬프트를 커밋해 고정한 뒤 새 공고(PDF 있는 것 최대 5건)를 받아 한 번만 잰다. 그 뒤로 프롬프트를 고치지 않는다
- jw 기준은 새 공고 쪽 결과로 판정한다. 설계에 쓴 3건 결과는 옆에 같이 적는다

칸 하나(공고 × 필드)는 셋 중 하나다. 정답이 있는 칸만 센다.

| 칸 | 뜻 |
| --- | --- |
| 맞음 | 값이 있고 `normalize()`를 건 정답과 같다 |
| 비움 | 값이 비었다(LLM이 비웠거나 거르는 규칙이 비웠다) |
| 틀리게 채움 | 값이 있는데 정답과 다르다 |

틀리게 채운 칸은 리포트에 한 줄씩 원인을 적는다: `LLM 오답`(다른 숫자·다른 날짜를 골랐다) / `정규화`(같은 값인데 꼴이 달라 안 맞았다) / `정답 쪽`(청약홈 표 값이 PDF와 다르다). jw 기준의 두 번째 문장(못 하면 비운다)을 어긴 것은 `LLM 오답`뿐이다.
