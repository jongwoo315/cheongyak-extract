## 설계 결정

| 결정 | 고른 것 | 이유 |
| --- | --- | --- |
| 정규화 위치 | 비교 직전, 정답과 추출값 양쪽에 같은 함수 | 정답 쪽에도 값 아닌 글자(신문명·URL)가 붙어 있다. 한쪽만 고치면 다른 쪽 꼴이 남는다 |
| 함수 단위 | 필드 종류별(날짜·기간·월·회사명·세대수·주소) | 날짜 규칙을 회사명에 걸면 안 된다. `FIELDS`마다 종류를 하나 붙인다 |
| 원본 보존 | 리포트와 저장은 원본, 비교만 정규형 | 정규화가 틀렸을 때 원본이 있어야 되짚는다 |
| 못 읽는 값 | 정규화 실패면 원본 `strip()`으로 비교 | 조용히 빈 값으로 만들면 빈 칸·정확도가 둘 다 왜곡된다 |
| 잴 방법 | PDF에 적힌 꼴을 손으로 옮긴 「모의 추출값」 24쌍(3건 × 8필드) | stub 추출은 늘 빈 값이라 비교 품질을 못 잰다. PDF 원문 꼴을 추출값 자리에 넣으면, LLM이 PDF를 그대로 옮겼을 때 맞게 잡히는지를 미리 잰다 |
| 금액 단위 | 이번에 안 한다 | 지금 정답 필드에 금액이 없다(공급금액은 표 안의 반복 행이라 #146에서 뺐다) |

## 정규화 결과가 같아지면 안 되는 것

정규화가 너무 세면 다른 값도 같아진다. 아래는 같아지면 안 된다.

- 다른 날짜 (`2026-11-10` vs `2026-11-11`)
- 기간의 시작만 같은 것 (`2026-11-23 ~ 2026-11-25` vs `2026-11-23 ~ 2026-11-26`)
- 다른 회사 (`반도건설` vs `반도종합건설`)
- 다른 세대수 (`358세대` vs `385세대`)
- 빈 값과 빈 값이 아닌 것
